Cool — with C++11 you don’t have inline constexpr variables, so the header-only “globals” approach needs a slightly different pattern to avoid ODR / multiple-definition issues.

The most reliable C++11 + header-only pattern is:
	•	put your paths in a namespace
	•	expose them via inline functions that return a boost::filesystem::path
	•	keep the raw configured strings as macros (or static const char[]) generated by CMake

That keeps it “header-only”, avoids linker problems, and uses Boost’s path type.

⸻

1) Template header (configured by CMake)

Create cmake/project_paths.hpp.in:

#pragma once

#include <boost/filesystem/path.hpp>

namespace project {
namespace paths {

// These macros are filled in by CMake at configure time.
#define PROJECT_PREFIX     "@CMAKE_INSTALL_PREFIX@"
#define PROJECT_DATA_DIR   "@PROJECT_DATA_DIR@"
#define PROJECT_CONFIG_DIR "@PROJECT_CONFIG_DIR@"
#define PROJECT_CACHE_DIR  "@PROJECT_CACHE_DIR@"

// Header-only accessors returning boost::filesystem::path
inline boost::filesystem::path prefix()    { return boost::filesystem::path(PROJECT_PREFIX); }
inline boost::filesystem::path data_dir()  { return boost::filesystem::path(PROJECT_DATA_DIR); }
inline boost::filesystem::path config_dir(){ return boost::filesystem::path(PROJECT_CONFIG_DIR); }
inline boost::filesystem::path cache_dir() { return boost::filesystem::path(PROJECT_CACHE_DIR); }

// Convenience join helper
inline boost::filesystem::path data(std::string const& rel) {
    return data_dir() / rel;
}

} // namespace paths
} // namespace project

Why this works in C++11
	•	inline functions are fine in headers in C++11.
	•	Returning boost::filesystem::path constructs the object at the call site (no global variable definitions required).

(If you really hate macros, you can store static const char[] instead — see below.)

⸻

2) Top-level CMake: configure the header

set(PROJECT_DATA_DIR   "${CMAKE_SOURCE_DIR}/data")
set(PROJECT_CONFIG_DIR "${CMAKE_SOURCE_DIR}/config")
set(PROJECT_CACHE_DIR  "${CMAKE_BINARY_DIR}/cache")

configure_file(
  ${CMAKE_SOURCE_DIR}/cmake/project_paths.hpp.in
  ${CMAKE_BINARY_DIR}/generated/project_paths.hpp
  @ONLY
)


⸻

3) Make it visible to the entire project

Best practice: an INTERFACE library:

add_library(project_config INTERFACE)
target_include_directories(project_config INTERFACE
  ${CMAKE_BINARY_DIR}/generated
)

Then link it to every target:

target_link_libraries(my_target PRIVATE project_config)

And in code anywhere:

#include "project_paths.hpp"

auto p = project::paths::data("textures/foo.png");


⸻

Optional: avoid macros (still header-only, C++11-safe)

Replace the macro section with static arrays inside the namespace:

namespace project { namespace paths {

static const char prefix_str[]     = "@CMAKE_INSTALL_PREFIX@";
static const char data_dir_str[]   = "@PROJECT_DATA_DIR@";
static const char config_dir_str[] = "@PROJECT_CONFIG_DIR@";
static const char cache_dir_str[]  = "@PROJECT_CACHE_DIR@";

inline boost::filesystem::path prefix()     { return boost::filesystem::path(prefix_str); }
inline boost::filesystem::path data_dir()   { return boost::filesystem::path(data_dir_str); }
inline boost::filesystem::path config_dir() { return boost::filesystem::path(config_dir_str); }
inline boost::filesystem::path cache_dir()  { return boost::filesystem::path(cache_dir_str); }

} }

In C++11, static const char[] in a header gives each translation unit its own copy (fine for constants like this).

⸻

One more important CMake note (Boost)

If you use boost::filesystem, you usually need to link against Boost filesystem/system:

find_package(Boost REQUIRED COMPONENTS filesystem system)

target_link_libraries(my_target PRIVATE Boost::filesystem Boost::system project_config)

(Some toolchains can do header-only-ish behavior for newer Boost setups, but the safe assumption is you must link.)
